## 1. 데이터 유실 (Data Loss) 문제

- Docker 컨테이너는 기본적으로 휘발성 특정을 가진다.
- 컨테이너 내부 쓰기 레이어에 저장된 데이터는 컨테이너가 삭제되면 함께 사라진다.

### 1-1. Docker Compose 종료와 데이터 삭제

- `docker compose down` 명령을 실행하면 컨테이너가 중지되고 삭제된다.
- 이때 데이터베이스(MySQL, PostgreSQL 등) 컨테이너 내부에 생성된 테이블이나 레코드가 별도의 설정 없이는 모두 소멸된다.

## 2. Docker Volume이란?

> 컨테이너의 생명주기와 무관하게 데이터를 영속적으로 저장하기 위한 메커니즘

- 컨테이너가 삭제되어도 데이터는 호스트 머신의 특정 디렉토리에 안전하게 보관된다.
- 여러 개의 컨테이너가 동일한 볼륨을 동시에 마운트하여 데이터를 공유할 수 있다.
- 컨테이너의 쓰기 레이어보다 호스트 파일 시스템을 직접 이용하므로 입출력 성능이 우수하다.

```yml
services:
  db:
    image: mysql:8.4
    environment:
      MYSQL_ROOT_PASSWORD: password
      MYSQL_DATABASE: app_db
    ports:
      - "33061:3306"
    volumes:
      - db_data:/var/lib/mysql

volumes:
  db_data:
```

## 3. 추론 과정에서의 동시성 문제

- AI 모델, LLM, Transformer 계열의 모델을 서빙할 때는 일반적인 웹 API와는 다른 동시성 이슈가 발생한다.

```
대부분의 모델은 효율적인 추론을 위해 Key-Value Cache, Attention Buffer, Context 정보 등을 메모리에 유지한다.

- Thread-unsafe
이러한 모델 인스턴스는 기본적으로 여러 스레드가 동시에 접근하여 수정하도록 설계되어있지 않다.

- Race Condition 발생
여러 사용자가 동시에 요청을 보낼 경우, 하나의 모델 인스턴스 내부 상태를 여러 요청이 공유하게 된다.

→ 그 결과 A 유저의 질문 문맥에 B 유저의 문맥이 섞이거나 이전 요청의 결과가 현재 응답에 포함되는 등 잘못된 응답이 생성될 수 있다.
```

## 4. 동시성 문제 해결방안

- 모델 추론을 별도 Worker로 분리하고 Queue로 요청 전달

```
Queue란?
→ FIFO(First-In, First-Out)방식의 자료구조
→ 먼저 들어온 요청이 먼저 처리되는 대기열 역할을 수행
```

## 5. 동시성을 대비한 아키텍처

1. **FastAPI**: 클라이언트로부터 HTTP 요청 받아 추론 작업을 Queue에 추가
2. **Worker**: Queue를 모니터링하다가 작업이 들어오면 하나씩 꺼낸다. 모델 인스턴스에 접근하여 추론 수행
3. **상태 보호**: Worker는 한 번에 하나의 작업만 수행하므로 모델의 내부 상태가 섞이지 않음
4. **결과 전달**: 추론이 완료되면 결과를 Pub/Sub 구조를 통해 FastAPI에 전달
5. **응답**: FastAPI는 최종 결과를 클라이언트에게 전달
